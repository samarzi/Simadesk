## P0.1 — Убрать секретные ключи из кода и конфигов

### Зачем
Сейчас Supabase anon-key лежит открытым текстом в `netlify.toml` (строка 70) и в `.env` файле (1021 байт). Любой, кто получит доступ к репозиторию или истории деплоя, сможет читать и писать в базу данных. Даже если RLS настроен — anon-key не должен быть в Git.

### Что сделать

1. **Ротировать текущий Supabase ключ:**
   - Зайти в Supabase Dashboard → Settings → API → Regenerate anon key
   - Старый ключ после этого перестанет работать

2. **Перенести все секреты в Netlify Environment Variables:**
   - Netlify Dashboard → Site settings → Environment variables
   - Добавить переменные:
     ```
     VITE_API_URL=https://simadesk.ru
     VITE_API_KEY=<новый_ключ>
     VITE_TG_BOT_USERNAME=simadesk_bot
     ```
   - Vite автоматически подхватит `VITE_*` переменные при сборке

3. **Удалить секреты из netlify.toml:**
   - Убрать секцию `[context.production.environment]` с ключами (строки 68-73)
   - Оставить только build-конфиг и redirects

4. **Обновить .gitignore:**
   ```
   .env
   .env.local
   .env.production
   ```

5. **Удалить `.env` и `.env.production` из отслеживания** (если Git подключен):
   ```bash
   git rm --cached .env .env.production
   ```

### Критерии готовности
- В репозитории нет ни одного файла с реальными ключами
- Приложение работает на Netlify — ключи берутся из env variables
- Локально разработчик создаёт свой `.env` по шаблону `.env.example`

- После входа создаёт компанию или попадает в существующую
- Данные изолированы: пользователь видит только свои компании

## P0.3 — Разбить App.ts (6051 строка) на модули

### Зачем
`App.ts` — это god class, в котором лежит ВСЯ логика UI: рендеринг таблицы, карточек, импорт, экспорт, фильтры, поиск, сайдбар, модалки, drag-and-drop, виртуализация. При 6000+ строк:
- Невозможно работать двум разработчикам одновременно — постоянные merge-конфликты
- Ошибка в одном месте ломает всё
- Время на поиск нужного кода растёт линейно

### Как разбить

Предлагаемая декомпозиция (каждый модуль — отдельный файл):

```
src/
├── App.ts                    # Оркестратор: инициализация, роутинг между страницами
│                              # Целевой размер: 300-500 строк
├── views/
│   ├── TableView.ts          # Виртуализированная таблица (vtPaint, сортировка, drag столбцов)
│   ├── CardView.ts           # Карточный вид (сетка, рендеринг карточек)
│   ├── ProductDetail.ts      # Модалка детального просмотра товара (галерея, параметры)
│   └── ProductEditor.ts      # Редактирование товара (форма, сохранение)
├── components/
│   ├── Sidebar.ts            # Левый сайдбар (список коробок, навигация)
│   ├── FilterPanel.ts        # Панель фильтров (цена, динамические фильтры)
│   ├── SearchBar.ts          # Поиск с debounce и подсветкой
│   ├── ImportFlow.ts         # Весь флоу импорта (drag-drop, превью, конфликты, batch-вставка)
│   ├── ExportFlow.ts         # Экспорт (выбор столбцов/позиций, генерация xlsx)
│   ├── TopBar.ts             # Верхняя панель (кнопки, переключение видов)
│   └── MobileNav.ts          # Нижняя навигация для мобилы (bottom-sheet)
└── modules/                  # (уже существуют — не трогать)
    ├── OzonModule.ts
    ├── WbModule.ts
    └── ...
```

### Порядок разбиения (от простого к сложному)

1. **SearchBar.ts** — самый изолированный: debounce, regex, подсветка. Отрезать от App, экспортировать `{ query, onSearch }`
2. **FilterPanel.ts** — отфильтровать всё что связано с ценовым фильтром и динамическими фильтрами
3. **Sidebar.ts** — список коробок, счётчики, мобильный bottom-sheet
4. **ImportFlow.ts** — `parsedImport`, `importCtx`, модалки превью/конфликтов/новых столбцов
5. **ExportFlow.ts** — модалка экспорта, генерация файла
6. **TableView.ts** — виртуализация (`vt*`), сортировка, drag-drop столбцов
7. **CardView.ts** — рендеринг карточек
8. **ProductDetail.ts + ProductEditor.ts** — модалки просмотра и редактирования

### Как связывать модули

Использовать паттерн EventEmitter или простой callback-интерфейс:

```typescript
// SearchBar.ts
export class SearchBar {
  private onSearch: (query: string) => void;

  constructor(container: HTMLElement, onSearch: (query: string) => void) {
    this.onSearch = onSearch;
    // ... рендер инпута, debounce
  }
}

// App.ts
import { SearchBar } from './components/SearchBar';

class App {
  init() {
    this.searchBar = new SearchBar(
      document.getElementById('search-container')!,
      (q) => this.handleSearch(q)
    );
  }
}
```

### Критерии готовности
- App.ts не более 500 строк
- Каждый модуль/компонент можно открыть и понять за 2 минуты
- Все существующие функции работают как раньше (регрессия = 0)
- Два разработчика могут параллельно работать над SearchBar и ImportFlow без конфликтов

## P0.4 — Настроить CI/CD

### Зачем
Сейчас деплой на Netlify идёт без автоматических проверок. Сломанный TypeScript или упавший тест попадёт в production.

### Что сделать

**Вариант 1 — GitHub Actions (если репозиторий на GitHub):**

Создать файл `.github/workflows/ci.yml`:
```yaml
name: CI
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 18
          cache: npm
      - run: npm ci
      - run: npx tsc --noEmit        # проверка типов
      - run: npm test                  # vitest
      - run: npm run build             # сборка
```

**Вариант 2 — Netlify Build Plugin (проще, если нет GitHub):**

В `netlify.toml` добавить:
```toml
[build]
  command = "npm run build"  # уже есть

# Добавить pre-build шаг
[[plugins]]
  package = "@netlify/plugin-lighthouse"
```

И в `package.json` изменить build-скрипт:
```json
"build": "tsc --noEmit && vitest run && vite build"
```

### Критерии готовности
- При push в main: автоматически прогоняются тесты и проверка типов
- Если тесты падают — деплой не происходит
- Разработчик видит статус проверки в PR (если используется GitHub)

## P0.5 — Добавить Error Tracking (Sentry)

### Зачем
Когда пользователи начнут работать с продуктом, ошибки будут происходить: сетевые проблемы, невалидные данные от API маркетплейсов, баги в UI. Без Sentry вы не узнаете о них, пока пользователь не напишет в чат.

### Что сделать

1. **Зарегистрироваться на sentry.io** — бесплатный план: 5000 ошибок/мес

2. **Установить SDK:**
   ```bash
   npm install @sentry/browser
   ```

3. **Инициализировать в `src/main.ts`:**
   ```typescript

       dsn: import.meta.env.VITE_SENTRY_DSN,
       environment: 'production',
       release: '2.0.0',
       tracesSampleRate: 0.1,  // 10% запросов для трейсинга
     });
   }
   ```

4. **Добавить DSN в Netlify env variables:**
   ```
   VITE_SENTRY_DSN=https://xxx@sentry.io/yyy
   ```

5. **Оборачивать критичные вызовы:**
   ```typescript
   // В api.ts — уже есть единая обёртка api()
   // Добавить Sentry.captureException(err) в catch-блок
   ```

### Критерии готовности
- Ошибки в production автоматически попадают в Sentry
- Каждая ошибка содержит: стектрейс, браузер, URL, user ID (после auth)
- Настроены алерты: email при >10 ошибок за час

## P1.1 — Биллинг и подписка

### Зачем
Без монетизации нет бизнеса. Биллинг нужен до запуска первым клиентам, иначе потом придётся менять поведение приложения под имеющихся бесплатных пользователей.

### Что сделать

**Выбор платёжной системы:**
- **ЮKassa** — если клиенты из России (основной рынок). Комиссия 2.8%. Поддерживает рекуррентные платежи
- **Stripe** — если планируется международный рынок. Не работает с российскими картами напрямую

**Модель подписки (рекомендация):**

| Тариф | Цена | Что входит |
|-------|------|-----------|
| Free | 0 ₽ | 1 магазин, 100 товаров, базовая аналитика |
| Старт | 1 990 ₽/мес | 3 магазина, 5 000 товаров, все модули |
| Бизнес | 4 990 ₽/мес | 10 магазинов, 50 000 товаров, репрайсер, автобиддер |
| Корпоратив | 9 990 ₽/мес | Без ограничений, API, white-label, приоритетная поддержка |

**Реализация:**

1. **Таблицы в Supabase:**
   ```sql
   CREATE TABLE subscriptions (
     id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
     company_id UUID REFERENCES companies(id) ON DELETE CASCADE,
     plan TEXT NOT NULL CHECK (plan IN ('free', 'start', 'business', 'corp')),
     status TEXT DEFAULT 'active' CHECK (status IN ('active', 'cancelled', 'past_due', 'trialing')),
     current_period_start TIMESTAMPTZ,
     current_period_end TIMESTAMPTZ,
     payment_provider TEXT,         -- 'yookassa' | 'stripe'
     external_subscription_id TEXT, -- ID подписки во внешней системе
     created_at TIMESTAMPTZ DEFAULT NOW()
   );

   CREATE TABLE payments (
     id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
     company_id UUID REFERENCES companies(id),
     amount_rub NUMERIC NOT NULL,
     status TEXT DEFAULT 'pending',
     provider_payment_id TEXT,
     created_at TIMESTAMPTZ DEFAULT NOW()
   );
   ```

2. **Edge Function для webhook:**
   - ЮKassa отправляет webhook на `/api/payment-webhook`
   - Edge function проверяет подпись, обновляет `subscriptions.status`

3. **Лимиты в приложении:**
   ```typescript
   // companyService.ts — добавить проверку
   async canAddStore(): Promise<boolean> {
     const sub = await this.getSubscription();
     const storeCount = await this.getStoreCount();
     const limits = { free: 1, start: 3, business: 10, corp: Infinity };
     return storeCount < limits[sub.plan];
   }
   ```

4. **UI:**
   - Страница тарифов (доступна до оплаты и из настроек)
   - Баннер «Лимит исчерпан — обновите тариф» при достижении ограничений
   - Страница управления подпиской в настройках компании

### Критерии готовности
- Пользователь может выбрать тариф и оплатить
- Рекуррентные платежи работают автоматически
- При неоплате — доступ ограничивается до Free-тарифа (данные не удаляются)
- Есть 14-дневный триал на тарифе «Старт»

## P1.2 — Unit-экономика товара

### Зачем
Это самая запрашиваемая функция у продавцов. MPStats делает это плохо, MarketGuru — средне. Продавцу нужно видеть на каждый товар: выручка − себестоимость − комиссия МП − логистика − реклама = чистая прибыль. Без этого он не понимает, зарабатывает ли вообще.

### Что сделать

1. **Расширить таблицу себестоимости** (`cost_prices` — уже есть в `costPriceDb.ts`):
   ```sql
   ALTER TABLE cost_prices ADD COLUMN IF NOT EXISTS
     logistics_cost NUMERIC DEFAULT 0,
     packaging_cost NUMERIC DEFAULT 0,
     ads_cost NUMERIC DEFAULT 0;
   ```

2. **Создать модуль `src/modules/UnitEconomicsModule.ts`:**

   ```typescript
   interface UnitEconomics {
     sku: string;
     productName: string;
     sellingPrice: number;       // Цена продажи
     costPrice: number;          // Себестоимость закупки
     mpCommission: number;       // Комиссия маркетплейса (%)
     mpCommissionRub: number;    // Комиссия в рублях
     logisticsCost: number;      // Логистика (доставка до склада + до покупателя)
     packagingCost: number;      // Упаковка
     adsCostPerUnit: number;     // Реклама на единицу (общий бюджет / продажи)
     taxRate: number;            // Налог (УСН 6% или 15%)
     taxRub: number;
     netProfit: number;          // Чистая прибыль на единицу
     margin: number;             // Маржа (%)
     roi: number;                // ROI (%)
   }
   ```

3. **UI — две формы отображения:**
   - **Таблица** — все товары с колонками: цена, себестоимость, комиссия, логистика, маржа, прибыль. Сортировка по любой колонке. Красная подсветка убыточных товаров
   - **Калькулятор на карточке товара** — интерактивный: изменил цену → мгновенно пересчитало маржу и прибыль

4. **Откуда брать данные:**
   - Себестоимость — вводит пользователь (уже есть `costPriceDb`)
   - Комиссия МП — из API (Ozon: `/v1/product/info/prices`, WB: из карточки товара)
   - Логистика — средняя за период из финансовых отчётов (уже подтягиваются через `financeSync.ts`)
   - Реклама — общий бюджет / количество продаж за период

### Критерии готовности
- На каждый товар видна чистая прибыль в рублях и маржа в %
- Убыточные товары подсвечены красным
- Калькулятор «что будет если» — изменение цены мгновенно пересчитывает маржу
- Сводная таблица: общая прибыль за период по всем товарам

## P1.3 — Telegram-бот для уведомлений

### Зачем
Бот уже нужен для авторизации (P0.2). Расширить его на уведомления — минимальные затраты, но огромная ценность. Продавцы живут в Telegram, им не нужно заходить в веб-приложение чтобы узнать о проблеме.

### Что сделать

1. **Расширить бота:**
   ```
   Уведомления:
   - Новый заказ (> X₽)
   - Отзыв с рейтингом 1-2 звезды (нужен быстрый ответ)
   - Цена конкурента изменилась (если настроен репрайсер)
   - Товар закончился на складе
   - Репрайсер изменил цену
   - Подписка истекает через 3 дня
   ```

2. **Таблица настроек уведомлений:**
   ```sql
   CREATE TABLE notification_settings (
     id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
     user_id UUID REFERENCES users(id) ON DELETE CASCADE,
     company_id UUID REFERENCES companies(id) ON DELETE CASCADE,
     channel TEXT DEFAULT 'telegram',
     event_type TEXT NOT NULL,  -- 'new_order', 'bad_review', 'price_change', 'out_of_stock'
     enabled BOOLEAN DEFAULT true,
     min_amount NUMERIC,        -- для заказов: уведомлять только если сумма > X
     created_at TIMESTAMPTZ DEFAULT NOW()
   );
   ```

3. **Отправка через Telegram Bot API:**
   ```typescript
   // Edge Function: /api/notify
   async function sendTelegramNotification(telegramId: number, message: string) {
     await fetch(`https://api.telegram.org/bot${BOT_TOKEN}/sendMessage`, {
       method: 'POST',
       headers: { 'Content-Type': 'application/json' },
       body: JSON.stringify({
         chat_id: telegramId,
         text: message,
         parse_mode: 'HTML',
       }),
     });
   }
   ```

4. **Cron-задача** (Supabase pg_cron или внешний сервис):
   - Каждые 15 минут проверять новые заказы, отзывы, изменения цен
   - Отправлять уведомления тем, у кого включена настройка

### Критерии готовности
- Пользователь получает уведомление в Telegram при новом заказе
- В настройках можно включить/выключить каждый тип уведомлений
- Бот не спамит: дедупликация (не отправлять повторно про тот же заказ)

## P1.4 — Увеличить покрытие тестами

### Зачем
Сейчас 9 тестовых файлов на 30 000+ строк кода — это менее 1% покрытия. При рефакторинге App.ts (P0.3) без тестов нельзя гарантировать отсутствие регрессий. Каждый баг в продакшне = потеря клиента.

### Что сделать

**Приоритет тестирования (от критичного к желательному):**

1. **Сервисы API** — самое важное, потому что ошибка здесь = потеря данных:
   ```
   src/services/api.ts          — CRUD операции, обработка ошибок
   src/services/ozonApi.ts      — парсинг ответов Ozon API
   src/services/wbApi.ts        — парсинг ответов WB API
   src/services/yandexApi.ts    — парсинг ответов Яндекс API
   src/services/financeSync.ts  — расчёт финансов (ошибка = неверные цифры)
   src/services/authService.ts  — авторизация (ошибка = утечка доступа)
   ```

## P2.1 — PWA + Service Worker

### Зачем
Продавцы часто работают со складов и точек выдачи, где нестабильный интернет. PWA позволяет:
- Работать с кэшированными данными офлайн
- Установить приложение на рабочий стол телефона (без App Store)
- Получать push-уведомления

### Что сделать

1. **Создать `public/manifest.json`:**
   ```json
   {
     "name": "SimaDesk — Marketplace Manager",
     "short_name": "SimaDesk",
     "start_url": "/",
     "display": "standalone",
     "background_color": "#0d0d0d",
     "theme_color": "#d4f000",
     "icons": [
       { "src": "/logo-192.png", "sizes": "192x192", "type": "image/png" },
       { "src": "/logo-512.png", "sizes": "512x512", "type": "image/png" }
     ]
   }
   ```

2. **Создать Service Worker `public/sw.js`:**
   ```javascript
   const CACHE_NAME = 'simadesk-v1';
   const STATIC_ASSETS = ['/', '/index.html', '/logo-192.png'];

   self.addEventListener('install', (e) => {
     e.waitUntil(caches.open(CACHE_NAME).then(c => c.addAll(STATIC_ASSETS)));
   });

   self.addEventListener('fetch', (e) => {
     // Network-first для API, cache-first для статики
     if (e.request.url.includes('/rest/v1/') || e.request.url.includes('-api/')) {
       e.respondWith(
         fetch(e.request)
           .then(r => { caches.open(CACHE_NAME).then(c => c.put(e.request, r.clone())); return r; })
           .catch(() => caches.match(e.request))
       );
     } else {
       e.respondWith(caches.match(e.request).then(r => r || fetch(e.request)));
     }
   });
   ```

3. **Зарегистрировать в `src/main.ts`:**
   ```typescript
   if ('serviceWorker' in navigator && import.meta.env.PROD) {
     navigator.serviceWorker.register('/sw.js');
   }
   ```

4. **Добавить иконку 512x512** — нужна для установки на Android

### Критерии готовности
- Chrome показывает кнопку «Установить» в адресной строке
- После установки — приложение открывается как нативное (без адресной строки)
- При потере интернета — показываются кэшированные данные с баннером «Оффлайн-режим»
- Lighthouse PWA score: 90+

## P2.2 — Автобиддер (управление рекламными ставками WB)

### Зачем
MPStats берёт за автобиддер 7 990 ₽/мес отдельно. Это высокомаржинальная функция: продавцы, тратящие на рекламу 50-500k ₽/мес, готовы платить за автоматизацию. Включение этой функции в тариф «Бизнес» — сильное конкурентное преимущество.

### Что сделать

1. **Создать модуль `src/modules/AutoBidderModule.ts`:**

   ```
   Стратегии ставок:
   1. «Удержание позиции» — не давать ставке упасть ниже топ-N
   2. «Бюджет на день» — распределить X₽ равномерно за день
   3. «По ROI» — если ROI рекламы < порога → снижать ставку
   4. «Время суток» — повышенные ставки в пиковые часы (10-14, 19-22)
   ```

2. **WB Promotion API:**
   ```
   Эндпоинты:
   POST /adv/v1/budget/deposit — пополнить бюджет кампании
   GET  /adv/v1/promotion/adverts — список рекламных кампаний
   POST /adv/v1/promotion/update — обновить ставку
   ```

3. **Таблица правил:**
   ```sql
   CREATE TABLE bidder_rules (
     id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
     company_id UUID REFERENCES companies(id) ON DELETE CASCADE,
     store_id UUID NOT NULL,
     mp TEXT NOT NULL CHECK (mp IN ('wb')),
     campaign_id TEXT NOT NULL,
     strategy TEXT NOT NULL,        -- 'hold_position' | 'daily_budget' | 'roi' | 'time_of_day'
     params JSONB NOT NULL,         -- параметры стратегии
     status TEXT DEFAULT 'active',
     last_run_at TIMESTAMPTZ,
     last_result JSONB,
     created_at TIMESTAMPTZ DEFAULT NOW()
   );
   ```

4. **Cron-задача (каждые 30 минут):**
   - Считать активные правила
   - Получить текущие ставки и статистику
   - Рассчитать новую ставку по стратегии
   - Обновить через API
   - Записать лог изменения

### Критерии готовности
- Пользователь может создать правило для рекламной кампании WB
- Ставки обновляются автоматически каждые 30 минут
- История изменений ставок с причиной каждого изменения
- Защита: минимальная и максимальная ставка, дневной лимит бюджета

## P4.1 — Мобильное приложение

### Зачем
60%+ продавцов заходят проверить заказы и отзывы с телефона. PWA (P2.1) закрывает часть потребностей, но нативное приложение даёт push-уведомления, лучшую производительность и доверие через присутствие в App Store / Google Play.

### Варианты реализации
- **React Native** — если в команде есть React-опыт. Один код на iOS + Android
- **Flutter** — если хочется производительность ближе к нативной
- **Capacitor + текущий код** — обернуть веб-приложение в нативную оболочку (самый быстрый путь, но ограниченные возможности)

### Минимальный набор для мобилки:
- Просмотр заказов и отзывов
- Уведомления (push)
- Быстрая аналитика (выручка сегодня, заказы)
- Ответ на отзывы

## P4.2 — AI-функции

### Зачем
Конкуренты начинают добавлять AI, но пока слабо. Можно выйти с лучшим решением, ЕСЛИ основа продукта стабильна (поэтому AI — в последнюю очередь, как указано в ROADMAP).

1. **Генерация описаний карточек:**
   - Ввод: название товара + характеристики + ключевые слова
   - Claude/GPT API → оптимизированное SEO-описание
   - Предпросмотр и редактирование перед публикацией

2. **Рекомендации по цене:**
   - Анализ цен конкурентов + собственные продажи + сезонность

3. **Прогноз спроса:**
   - На основе истории продаж — прогноз на 2-4 недели

4. **Автоответы на отзывы (AI):**
   - Анализ тональности отзыва
   - Генерация ответа с учётом контекста (негатив → извинение + решение, позитив → благодарность)
